# Setlist Builder backend

Go API service with MongoDB connectivity.

## Run locally

1. Install Go 1.22 or newer.
2. Keep MongoDB values in `backend/.env`.
3. From this directory, run:

```bash
go mod tidy
go run ./cmd/server
```

The API starts on `http://localhost:8080`. Check the MongoDB connection with:

```bash
curl http://localhost:8080/health
```

## API routes

All write endpoints accept and return JSON. IDs are generated by the backend.

| Page / feature | Method | Route |
| --- | --- | --- |
| Login unlock | `POST` | `/api/auth/unlock` |
| Current authenticated user | `GET` | `/api/auth/me` |
| Song library search | `GET` | `/api/songs?q=hotel` |
| Add song | `POST` | `/api/songs` |
| View/edit song | `GET`, `PATCH`, `DELETE` | `/api/songs/{id}` |
| Chord builder/editor | `GET`, `PUT` | `/api/songs/{id}/chords` |
| Setlist builder | `GET`, `POST` | `/api/setlists` |
| Setlist song entries | `GET`, `POST`, `DELETE` | `/api/setlists/{id}/entries[/{entryID}]` |
| Stage view state | `GET`, `PUT` | `/api/setlists/{id}/stage` |

`POST /api/auth/unlock` expects `{"passcode":"..."}` and compares it with
`ADMIN_PASSCODE`. It returns `503` until that environment value is configured.

## Database initialization and authentication

On startup the backend explicitly creates these collections if they do not
exist:

- `songs`
- `chord_charts`
- `setlists`
- `setlist_entries`
- `stage_snapshots`
- `users`
- `auth_sessions`

The admin account is seeded or updated from `ADMIN_USERNAME` and
`ADMIN_PASSCODE`. Passcodes are stored as bcrypt hashes. Login is:

Add these values to the real `backend/.env` file before starting the server
(do not commit that file):

```env
ADMIN_USERNAME=admin
ADMIN_PASSCODE=choose-a-private-passcode
```

```bash
curl -X POST http://localhost:8080/api/auth/unlock \
  -H 'Content-Type: application/json' \
  -d '{"passcode":"your-admin-passcode"}'
```

Use the returned token for all other `/api` requests:

```bash
curl http://localhost:8080/api/auth/me \
  -H 'Authorization: Bearer your-token'
```

Sessions expire after 24 hours and are automatically removed by MongoDB's TTL
index. Startup also creates indexes for song search, chord charts, stage
snapshots, setlist ordering, users, and sessions.

## Standalone Local Stage Relay

The Stage Relay is a separate server for offline gigs. It does not connect to
MongoDB or require internet access. From the repository root, build the
React app, embed it in the relay, and cross-compile for Android/Termux with:

```bash
make build-android
```

The binary is written to `backend/bin/stage-relay-arm64`. Before the gig,
export the setlist from the Admin Console as a gig-pack JSON file and copy both
that file and the binary to the Android phone that will host the hotspot.
Install Termux, open it, and copy the files from Downloads into Termux's
private home directory (Android shared storage may not allow executing a
binary directly):

```bash
termux-setup-storage
mkdir -p ~/stage-relay
cp ~/storage/downloads/stage-relay-arm64 ~/stage-relay/
cp ~/storage/downloads/your-gig-pack.json ~/stage-relay/gig-pack.json
cd ~/stage-relay
chmod +x stage-relay-arm64
./stage-relay-arm64
```

Start the Android hotspot, then run the relay in Termux. It listens on
`0.0.0.0:8080` and stores `gig-pack.json` beside the binary. Connect every
phone and laptop to that hotspot and open
`http://<android-hotspot-ip>:8080/stage`; find the hotspot IP in the connected
device's Wi-Fi network details (it is often `192.168.43.1`, but can vary).
Keep Termux running and exempt it from Android battery optimization during the
gig. No laptop or internet connection is needed at performance time; the
Android phone hosts the relay, and every bandmate's device is a Stage client.
Devices cache the setlist and songs locally. The relay exposes
`GET /api/stage/gig-pack`, `POST /api/stage/gig-pack`, and `/ws` live sync.

iOS Safari can open the local Stage URL, but iOS may restrict PWA installation,
offline app-shell reloads, and wake-lock features over plain HTTP.

For local development, run `npm run build:stage-relay` before building or
running `go run ./cmd/stage-relay` from `backend/`; this places the Vite
production assets in the relay's embedded web directory.
